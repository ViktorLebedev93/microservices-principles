Решение должно соответствовать следующим требованиям:

- обеспечение терминации HTTPS.

Обоснуйте свой выбор.

### Категоризация по сценариям использования

#### Универсальные решения (on-prem/гибридные)
- **Kong** - готовое решение API Gateway
- **NGINX** - максимальная производительность и гибкость
- **Tyk** - аналитика и управление API

#### Управляемые облачные сервисы
- **AWS API Gateway** - для инфраструктуры полностью в AWS
- **Azure API Management** - для инфраструктуры полностью в Azure

Для большинства случаев в крупной компании:

**Kong или NGINX** как наиболее сбалансированные решения

**Причины:**
- Универсальность (поддерживают on-premise и облачные развертывания)
- Высокая производительность (Kong построен на NGINX)
- Отсутствие vendor lock-in (не привязывают к конкретному облачному провайдеру)
- Полное соответствие требованиям ТЗ (маршрутизация, аутентификация, HTTPS)
- Активные сообщества и хорошая документация

## Задача 2: Брокер сообщений

Составьте таблицу возможностей различных брокеров сообщений. На основе таблицы сделайте обоснованный выбор решения.

Решение должно соответствовать следующим требованиям:

## Сравнительная таблица брокеров сообщений

| **Форматы сообщений** | Любые бинарные | Любые бинарные | Любые бинарные | Любые бинарные | Любые бинарные |

| **Гарантии доставки** | At-least-once | At-least-once | Best-effort | At-least-once | At-least-once |

## Рекомендуемое решение: **RabbitMQ**

### Обоснование выбора:

1. **Полное соответствие требованиям ТЗ:**
   - ✅ **Кластеризация**: Mirroring queues обеспечивает надёжность и отказоустойчивость
   - ✅ **Хранение на диске**: Сообщения сохраняются до подтверждения доставки
   - ✅ **Высокая скорость**: 50K+ сообщений/сек достаточно для большинства корпоративных систем
   - ✅ **Форматы сообщений**: Поддержка любых бинарных форматов (JSON, XML, Protobuf)
   - ✅ **Разделение прав**: Virtual Hosts + система пользователей и ACL
   - ✅ **Простота эксплуатации**: Встроенный Web UI, понятная документация

2. **Преимущества для крупной компании:**
   - **Проверенная надёжность**: Более 10 лет в production
   - **Гибкость**: Поддержка AMQP, MQTT, STOMP протоколов
   - **Экосистема**: Более 30 плагинов, интеграция с Prometheus, Grafana
   - **Сообщество**: Активная поддержка, коммерческие варианты

### Почему не другие решения:

- **Apache Kafka**: Слишком сложен для базовых нужд, требует отдельного ZooKeeper
- **Redis Streams**: Не гарантирует доставку, ориентирован на максимальную скорость
- **Apache Pulsar**: Менее зрелая экосистема, сложнее в эксплуатации
- **NATS JetStream**: Меньшее распространение, ограниченная функциональность

### Альтернативные сценарии:

- **Apache Kafka**: Если нужна обработка потоков данных и долгосрочное хранение
- **Redis Streams**: Если скорость критична, а потеря сообщений допустима
- **Управляемые сервисы** (Amazon SQS, Azure Service Bus): Если инфраструктура в облаке

### Вывод:

Для микросервисной архитектуры крупной компании **RabbitMQ** является оптимальным выбором, так как обеспечивает наилучший баланс между надёжностью, производительностью и простотой эксплуатации, полностью соответствуя всем требованиям ТЗ.
